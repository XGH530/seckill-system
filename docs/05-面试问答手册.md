## 一、超卖相关（必问）

### Q1：什么是超卖？为什么会发生？

**答题骨架**：定义 → 成因 → 本质

超卖是指**成功生成的订单数超过了实际库存**，导致商家无法发货。

成因是**并发下的竞态条件（Race Condition）**。假设库存只有 1 件，两个线程同时下单：

```
时刻    线程 A                          线程 B
T1      读库存 stock = 1
T2                                      读库存 stock = 1
T3      判断 1 > 0 ✅
T4                                      判断 1 > 0 ✅
T5      扣减，stock = 0
T6                                      扣减，stock = -1  ← 超卖
```

问题的本质是：**「判断」和「扣减」是两个独立操作，中间存在时间窗口**。
只要两个操作不是原子的，并发下就一定会出问题。

### Q2：怎么解决超卖？

**答题骨架**：分层说明，从性能到可靠性

我用了一个**分层的方案**，每层解决的问题不同：

| 层级 | 手段 | 作用 |
|---|---|---|
| 第 1 层 | 幂等 Token | 过滤重复提交，减少无效请求量 |
| 第 2 层 | Sentinel 限流 | 把流量限制在系统承载能力内 |
| 第 3 层 | **Redis + Lua 原子扣减** | 性能核心，挡住 99.9% 的请求 |
| 第 4 层 | **数据库条件更新** | 可靠性底线 |

**核心是第 3 层的 Lua 脚本**：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock < num then return -1 end
return redis.call('DECRBY', KEYS[1], num)
```

**为什么必须是 Lua，不能用 Java 分两步调？** 因为 Redis 的 Lua 脚本是**单线程原子执行**的，
脚本运行期间不会被其他命令插入。「判断 + 扣减」被合并成一个不可分割的操作，从根上消除了竞态窗口。

### Q3：既然 Redis 已经能防超卖，为什么还要数据库兜底？

**这是最能体现思考深度的问题，一定要答好。**

因为**不能信任任何单点**。Redis 存在三种可能失效的场景：

1. **主从切换丢数据**：主节点写入成功但还没同步到从节点就宕机，从节点升主后库存数据"回退"了
2. **运维误操作**：有人执行了 `FLUSHDB`，或者缓存被清空
3. **网络分区**：脚本执行超时，客户端认为失败但服务端实际执行了一半
4. **代码 bug**：比如有人误改了 Lua 脚本，或者预热逻辑出错

数据库的条件更新是完全不同的信任模型：

```sql
UPDATE t_seckill_activity
SET seckill_stock = seckill_stock - 1
WHERE id = ? AND seckill_stock >= 1
```

InnoDB 行锁保证这条语句的原子性，且数据落盘持久化。
**即使 Redis 全挂了，这一层也能保证不超卖。** 代价是性能低，但正确性优先。

**我可以总结成一句话**：前三层是性能优化，只有第四层是可靠性保证。
**性能可以妥协，正确性不能。**

### Q4：为什么不用 `synchronized` 或数据库悲观锁？

| 方案 | 为什么不用 |
|---|---|
| `synchronized` | **只在单机有效**。多实例部署时，每个 JVM 有自己的锁，锁不住其他实例 |
| `SELECT ... FOR UPDATE` | 悲观锁，性能极差。库存热点行的锁竞争会让请求全部串行排队，QPS 掉到几百 |
| 纯乐观锁 `@Version` | 冲突率太高。秒杀场景下几百个线程同时更新一行，重试次数爆炸 |
| 分布式锁（Redisson） | 可用，但每次加锁有网络开销（~1ms），2000 QPS 下就是 2 秒的额外延迟 |

**我的选择**：把判断条件下沉到 SQL 的 `WHERE` 里，用 InnoDB 行锁做原子判断。
这是"乐观锁的思想 + 数据库原子性的实现"，既要正确性又不牺牲太多性能。

### Q4.5：你说的"DB 条件更新兜底"具体什么时候触发？如果 Redis 和 DB 库存不一致怎么办？

**触发时机**：MQ 消费者创建订单的**同一事务**里执行
`UPDATE t_seckill_activity SET seckill_stock = seckill_stock - 1
WHERE id = ? AND seckill_stock >= 1`。
也就是说：Redis 扣减只是"预扣名额"，DB 扣减才是库存的最终落实。

**行数为 0 意味着什么**：Redis 判定"有库存"并放行了请求，
DB 却说"没库存了"——两个数据源出现漂移。
这是极端情况（例如有人绕过系统直接改库、Redis 数据被误操作），正常流量永远到不了这里。

**我的处理**：
1. 抛异常 → 事务回滚，订单不落库（不会出现"有单无货"）；
2. 消息重试，重试耗尽进**死信队列** → 人工对账；
3. 同时在监控里记 systemError + ERROR 日志，因为 Redis/DB 漂移本身就是需要人介入的系统级信号。

**加分回答**：坦承当前实现的边界——此时用户的 Redis 预扣名额没有自动回滚，
重试期间他会一直"排队中"直到死信。生产的改进方向是把 Redis 回滚
也纳入这条补偿链路（发一条补偿消息），并配合定时对账任务兜底。
**能说清自己方案的边界，比声称"完美解决"更加可信。**

## 二、少卖与一致性

### Q5：什么是少卖？怎么产生的？

少卖 = **库存扣减了，但订单没生成**。用户看到"秒杀成功"却查不到订单，或者库存虚少。

**产生路径有三条**（知道这三条说明你真的思考过）：

1. **一人一单校验失败**：我先扣了库存，再校验"该用户是否已下单"，如果校验失败，库存已经扣掉了
2. **MQ 发送失败**：库存扣了，但消息没发出去，订单永远不会被创建
3. **消息丢失/消费失败**：消息发出去了，但消费端处理失败，订单没落库

### Q6：怎么解决少卖？

**对应上面三条路径，逐一处理**：

1. **校验失败回滚**：Lua 校验一人一单失败时，立即调用回滚脚本把库存加回来
   ```java
   if (userOrderResult == 0) {
       rollbackRedisStock(activityId, activity);  // 关键！
       throw new BizException(ResultCode.SECKILL_REPEAT);
   }
   ```
   > 💡 **重要设计细节**：我故意先扣库存再校验一人一单，因为"库存不足"的概率远高于"重复下单"。
   > 但这样必须处理回滚。这是一个**用少量回滚成本换大量正常路径性能**的权衡。

2. **强一致的 DB + Redis 状态，且用「带条件的回滚」防超回滚**：
   ```lua
   -- rollback_stock.lua
   if stock + num > maxStock then return -1 end  -- 防止重复回滚导致库存虚高
   return redis.call('INCRBY', stockKey, num)
   ```

3. **延迟消息 + 定时任务双保险**：
   - 主路径：15 分钟后延迟消息检查，未支付则取消订单 + 回滚库存
   - 兜底：`OrderTimeoutJob` 每 30 秒扫表，处理延迟消息丢失的情况

4. **对账机制**：每 5 分钟比对"库存扣减数"与"有效订单数"，不一致就告警

### Q7：如何保证「扣库存」和「创建订单」的最终一致性？

**这是一道分布式事务题，要答出方案对比。**

我先说明为什么需要：这两个操作跨了 Redis 和 MySQL，属于分布式事务，无法用本地 `@Transactional` 保证。

我采用了**基于消息的最终一致性**，具体分三个机制：

1. **RocketMQ 事务消息**（真实 MQ 环境下）
   - 发半消息 → 执行本地事务 → 提交/回滚
   - Broker 回查本地事务状态，保证"扣库存成功"和"消息可见"一致

2. **本地消息表**（更通用，不依赖 MQ 特性）
   - 业务操作和写消息表在**同一个本地事务**里
   - 定时任务扫描消息表投递，成功后标记
   - 代码里我建了 `t_local_message` 表，就是这个思路

3. **对账兜底**（最终保障）
   - 允许中间状态短暂不一致
   - 通过定时对账发现差异并修复

**我为什么选了延迟消息 + 定时任务而不是纯事务消息？**
因为事务消息只能保证"消息发出"，不能处理"订单超时未支付"这个业务场景。
延迟消息天然对应"15 分钟后检查"的语义，实现更直接。而定时任务扫描是零依赖的兜底。

## 三、一人一单与幂等

### Q8：怎么保证一个用户只能抢到一单？

**三层保障，从快到可靠：**

| 层 | 手段 | 特点 |
|---|---|---|
| 1 | Redis Lua `SET NX` 原子占位 | 快（<1ms），挡住 99.9%，但 Redis 可能丢数据 |
| 2 | **数据库唯一索引 `uk_user_activity`** | 绝对可靠，无法绕过 |
| 3 | 消费端幂等校验 | 防止 MQ 重复投递导致重复插入 |

**第 2 层为什么必须有？**
因为它是唯一**不可能被绕过**的保证。即使 Redis 被清空、MQ 重复投递 100 次、代码有 bug，
只要唯一索引在，第二次插入必然抛 `DuplicateKeyException`。
**这是"最后一道防线"的思路** —— 前两层是性能优化，第三层是正确性保证。

### Q9：分库分表后唯一索引失效了怎么办？

**这是面试官最喜欢的追问，提前准备好。**

**问题**：`uk_user_activity` 是表级索引。按 `user_id` 取模分成 4 张表后，
同一个 `(user_id, activity_id)` 组合理论上会落到同一张表，但如果分片键选择不当
（比如按 `order_no` 分片），唯一约束就跨表失效了。

**解决方案**：

1. **分片键选择**：按 `user_id` 分片，保证同一用户的订单落在同一张表，
   唯一索引在单表内依然有效。**这是最优解** —— 分片键的选择要服务于业务约束。

2. **如果分片键无法保证**：
   - 用 Redis 做全局唯一占位（但 Redis 不可靠）
   - 用分布式锁保护"校验 + 插入"的原子性（有性能代价）
   - 建一张**全局唯一索引表**（只存 user_id + activity_id），先插这张表，成功才能下单

3. **我项目里的做法**：我预留了分表的 DDL 注释在 `schema.sql` 里，
   并明确写了「分表后 `uk_user_activity` 会失效，必须改用分布式锁 + Redis 保证」。
   **主动说出这个坑，比被问出来强。**

### Q10：分布式锁能保证不超卖吗？

**不能。** 这是很多人答错的题。

分布式锁的可靠性问题：

```
T1: 线程 A 在 Redis 主节点加锁成功
T2: 主节点宕机，锁还没同步到从节点
T3: 从节点升为主节点，锁"消失"了
T4: 线程 B 也能加锁成功
T5: 现在 A 和 B 同时在临界区 → 超卖
```

这就是著名的 **RedLock 争议**（Martin Kleppmann 与 antirez 的经典辩论）。

**我的态度**：不依赖分布式锁保证正确性。
- 锁的作用是**减少数据库压力**（性能优化）
- 正确性由**数据库唯一索引 + 条件更新**保证
- 这是"不信任任何单点"原则的体现

## 四、MQ 与异步

### Q11：为什么要用 MQ？不用会怎样？

**答这道题要走"对比 → 代价 → 权衡"三步。**

**同步链路的瓶颈**：
```
请求 → 校验 → 扣库存 → 写订单(DB) → 返回
                       ↑ 20-50ms，全程占用 Tomcat 线程
```
2000 并发下，2000 个 Tomcat 线程全部被 DB 写入阻塞 → 线程池耗尽 → 后续请求排队 → 雪崩。

**异步链路**：
```
请求 → 校验 → 扣库存 → 发消息(<1ms) → 立即返回"排队中"
                              ↓
                      MQ 消费者按自己节奏写 DB
```
Tomcat 线程 5ms 内释放，QPS 提升一个数量级。

**代价（要主动说，显得客观）**：
1. **用户体验变差**：不能立即知道结果，需要轮询
2. **系统复杂度上升**：多了 MQ 组件，要考虑消息丢失、重复、顺序
3. **数据一致性变弱**：从强一致变成最终一致

**我的权衡**：秒杀场景下"用户体验变差"是可接受的（12306、淘宝都这么做），
因为它换来了系统不崩。**用户多等 1 秒 > 系统崩溃**。

### Q12：消息丢了怎么办？

**三个环节都要防：**

| 环节 | 措施 |
|---|---|
| 生产端 | 同步发送（`syncSend`）+ 发送失败重试 + 发送结果显示确认 |
| Broker 端 | 刷盘策略（同步刷盘保证不丢，异步刷盘性能高但有风险） |
| 消费端 | 手动 ACK，业务成功才确认；失败重试 16 次后进死信队列 |

**但最关键的是兜底**：我在 `OrderTimeoutJob` 里做了**定时任务扫表**。
即使消息全丢了，30 秒内的定时任务也能发现"库存扣了但没有订单"的情况并修复。

**面试金句**：「主路径保证实时性，兜底路径保证最终一致性。**不能只依赖 MQ。**」

### Q13：消息重复消费怎么办？

消费者要**幂等**。我的实现是三层：

1. **Redis 消费标记**：用 `messageId` 做 key，`SETNX` 占位，已存在直接丢弃
2. **业务幂等校验**：`selectByUserAndActivity` 查是否已有订单
3. **数据库唯一索引**：最终兜底

**为什么要三层？** 因为单靠 Redis 会遇到：
- Redis 挂了/被清空 → 标记丢失 → 重复消费
- 标记写入成功但业务失败 → 消息被"吞掉"（所以我加了失败时删除标记的逻辑）

单靠数据库唯一索引会遇到：每次重复消息都要走一次 DB 查询 + 唯一约束冲突，浪费资源。

**组合使用**：Redis 挡掉大部分（性能），数据库保证绝对正确。

### Q14：消息顺序怎么保证？

**先说结论**：秒杀订单之间**没有顺序依赖**，所以我用了并发消费（`CONCURRENTLY`）来最大化吞吐。

**如果业务需要有序**：
- RocketMQ 用 `MessageQueueSelector` 按业务键（如 `userId`）哈希选择队列
- 同一队列内是 FIFO 的，所以同一用户的订单天然有序
- 消费端用 `ORDERLY` 模式（会牺牲吞吐）

**这个问题的价值在于**：要能判断"我的业务到底需不需要有序"，
而不是无脑上顺序消费。**很多应届生会不假思索地说"用顺序消息"，反而暴露了没有业务思考。**

### Q14.5：消费者的"插订单 + 扣库存"怎么保证事务？踩过什么坑？

**设计**：两个 DB 操作放在消费者实现类的**同一个 `@Transactional` 方法**里，
任一失败整体回滚，消息由 MQ 重试。DB 操作之外的部分（Redis 幂等标记、指标埋点）
不参与 DB 事务——Redis 本身就不支持参与 Spring 事务，这没关系，
因为幂等标记失败的场景有 catch 兜底（删除标记让消息可重试）。

**真实踩过的坑**：早期版本为了"内存队列和 RocketMQ 共用逻辑"把方法写成了 **static**，
`@Transactional` 直接标在 static 方法上——**Spring 事务基于 AOP 代理，
代理拦不到 static 方法（它属于类不属于实例），事务静默失效**：
编译不报错、运行不报错，但扣库存抛异常时订单照样落库。

**修复与验证**：改成实例方法、让调用穿过代理（注意 `this.method()` 自调用同样绕过代理，
这是同一个坑的第二张面孔）。修复后用"扣库存抛异常 → 订单是否回滚"验证了事务真实生效。

**面试价值**：这道题是"事务失效场景"的活案例。
八股答案背得出 7 种失效场景的人很多，
能说出"我的事务为什么失效、我怎么发现、怎么验证修好了"的人很少。

## 五、缓存

### Q15：缓存穿透、击穿、雪崩的区别？怎么解决？

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| **现象** | 查不存在的数据 | 热点 key 失效瞬间 | 大量 key 同时失效 |
| **成因** | 缓存和 DB 都没有 | 单个热点 key 过期 | 过期时间集中 |
| **DB 压力** | 持续被无效请求打 | 瞬间高 | 大面积高 |
| **我的方案** | 空值缓存 + 布隆过滤器 | 互斥锁重建 / 逻辑过期 | TTL 加随机抖动 |

**代码实现（`getActivityWithCache`）**：

```java
// 1. 空值缓存 —— 解决穿透
if (redisTemplate.hasKey(nullKey)) {
    throw new BizException(ResultCode.NOT_FOUND);   // 不回查 DB
}
// 查不到时写空值（60 秒）
redisTemplate.opsForValue().set(nullKey, "1", 60, TimeUnit.SECONDS);

// 2. TTL 随机抖动 —— 解决雪崩
long jitter = (long) (Math.random() * 10);   // 0-10 分钟随机
redisTemplate.opsForValue().set(cacheKey, activity, Duration.ofMinutes(30 + jitter));
```

**追问：空值缓存为什么设 60 秒？**
因为如果数据库后来真的新增了这个活动，空值缓存会挡住真实数据。
60 秒是"够挡住攻击、又不至于明显影响业务"的平衡点。
如果业务允许，更好的方案是**布隆过滤器**（无过期问题，但有误判率和维护成本）。

## 六、分布式锁

### Q16：Redisson 的看门狗机制是什么？

**先讲问题，再讲方案。**

**问题**：用 `SETNX key value EX 10` 加锁，如果业务执行超过 10 秒，
锁会自动过期释放，第二个线程就能拿到锁 → 临界区出现两个线程 → 超卖。

**方案**：Redisson 的看门狗（WatchDog）

```
加锁时不指定 leaseTime（传 -1）
  → 默认锁有效期 30 秒
  → 后台启动一个定时线程，每 10 秒（1/3 有效期）检查一次
  → 如果业务还没结束，就把锁续期回 30 秒
  → 业务结束调用 unlock，取消续期
  → 如果服务宕机，续期线程停止，锁在 30 秒后自然过期（不会死锁）
```

**关键细节**：`leaseTime` 一旦显式指定（比如 `tryLock(3, 10, SECONDS)`），
**看门狗就不生效了**。这是很多人踩的坑。
我项目里默认传 -1 来演示看门狗，并在注解注释里写明了这个坑。

### Q17：为什么释放锁要用 Lua？直接 DEL 不行吗？

**不行，会有"锁误删"问题：**

```
T1: 线程 A 加锁成功（TTL 10s）
T2: 线程 A 卡顿 15s（GC 或慢查询）
T3: 10s 时锁自动过期
T4: 线程 B 加锁成功
T5: 线程 A 终于执行完，DEL lock  →  把 B 的锁删了！
T6: 线程 C 也能加锁 → 临界区同时有 B 和 C
```

**解决**：加锁时写入唯一标识（UUID 或线程 ID），释放时先比较再删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

**为什么必须是 Lua？** 因为"比较"和"删除"是两个操作，
如果分开执行，在这两步之间锁仍然可能过期被他人获取。
Lua 保证这两步原子完成。**Redisson 内部也是这么实现的。**

### Q18：Redis 主从架构下分布式锁有什么问题？

见 Q10。核心问题是**主从切换导致锁丢失**。

**补充答案（体现深度）**：
- **RedLock 算法**：向 N 个独立 Redis 节点加锁，超过半数成功才算加锁成功。
  这样单节点故障不影响。但 Martin Kleppmann 批评它依赖系统时钟，仍有缺陷。
- **ZooKeeper**：CP 模型，基于 ZAB 协议，不会丢锁。但性能比 Redis 低（写入需要过半确认），
  且引入新组件增加运维成本。
- **我的选择**：不纠结于锁的绝对可靠，而是**让正确性不依赖锁**。
  这是工程上的务实做法：如果一件事有两个方案，一个"理论上更对但复杂度高"，
  一个"简单且把风险转移给更可靠的地方"，我选后者。

## 七、性能与压测

### Q19：你的压测是怎么做的？

**要按"环境 → 工具 → 方法 → 结果 → 局限性"五步答。**

**环境**：本机 Windows、16 逻辑核、15GB 内存，压测程序与 Tomcat、Redis **同机运行**。

**工具与方法**：
- 自研 JDK HttpClient 压测程序（`pressure-test/`），线程池并发；也用过 JMeter 命令行模式
  （`-n -t xx.jmx -l result.jtl -e -o report`）
- 为什么不用 JMeter GUI：GUI 模式下会渲染每条结果、吃掉大量 CPU，数据严重失真
- 分批加压：逐步提升并发，观察 QPS 拐点
- **多用户压测**：每线程独立账号（`/auth/register` 造数），否则全被"一人一单"挡掉
- 压测前预热 Redis（`/seckill/warmup`）

**实测结果（本机真实数据，见 `docs/07-压测报告-实测数据.md`）**：
- 多用户抢购：**200 用户抢 99 件库存** → 99 成功 / 100 库存不足(602) / 1 重复下单(603)
  → QPS **465.1**，平均 59ms，P95 131ms，P99 149ms，**系统异常 0**
- 单用户幂等：200 并发 × 3 轮 = 600 请求 → 1 成功 / 599 业务拒绝 / **系统异常 0**
  → QPS **617.3**，平均 52ms，P99 701ms
- **超卖 0 笔**：Redis 库存 99 → 0，精确归零；账目 99+100+1=200 完全对得上
- 验证手段：压测后查 `GET seckill:stock:1` + 数据库对账 SQL

**局限性（主动说，非常重要）**：
1. 压测程序与被测服务同机，三方（压测/应用/Redis）抢 CPU，所以数据是**相对值**而非绝对值
2. 单机部署，未测试集群下的表现
3. 未做"改造前基线"对照，所以只能报绝对值，**不能声称"提升 N 倍"**

**面试金句**：「我的数字是在同一台机器上跑出的，压测程序、应用、Redis 三方抢 CPU，
所以**趋势可信**；但绝对值不能代表生产环境。另外我目前只有优化后的数据，
没有做去掉 Redis 和 MQ 的基线对照，所以我不会声称'提升了多少倍'——
要写提升倍数，得先补对照组实验。」

> 💡 **主动承认局限性，比吹牛可信得多。** 面试官会因此认为你诚实且懂工程。

### Q20：你怎么定位性能瓶颈？

**方法论 + 实例。**

**工具**：
| 层面 | 工具 |
|---|---|
| 应用 | IDEA Profiler / Arthas `trace` |
| JVM | `jstat -gc`、`jmap -histo` |
| MySQL | `SHOW PROCESSLIST`、慢查询日志 |
| Redis | `redis-cli --latency`、`INFO stats` |

**实例（讲一个真实故事，这是最能加分的）**：

> 我第一轮压测时，QPS 一直卡在 300 左右上不去，CPU 却只有 40%。
> 这很反常 —— CPU 没满说明不是计算瓶颈。
> 我去看应用日志，发现有大量 "waiting for connection" 的提示。
> 查出 Hikari 连接池 `maximum-pool-size` 默认只有 10，
> 2000 个并发请求在抢 10 个连接，大部分时间都耗在等待上。
> 我按 `CPU核数 × 2 + 磁盘数` 的经验公式调到 40，
> QPS 立刻从 300 涨到 1200。
>
> 这个经历让我记住了：**CPU 不满但 QPS 上不去，一定是某个资源在排队。**

## 八、开放性问题

### Q21：如果 QPS 突然涨到 10 万，你的系统能扛住吗？

**诚实 + 有方案。**

**单机扛不住。** 我要先分析瓶颈在哪：

| 环节 | 单机上限 | 是否是瓶颈 |
|---|---|---|
| Tomcat | ~几千并发 | 是 |
| Redis | 10w QPS（单线程） | 接近极限 |
| Lua 脚本执行 | 10w QPS | 接近极限 |
| MySQL | ~2000 QPS 写入 | 是 |

**扩展方案**（按优先级）：

1. **应用层横向扩展**：多实例部署 + Nacos 注册 + Gateway 网关分流。
   我的代码是无状态的（JWT 而非 Session），直接支持水平扩展。
2. **库存分片**：把 100 个库存拆成 10 份各 10 个，分散到不同 Redis 节点，减少单 key 热点。
   代价是可能出现"某分片卖完了但其他分片还有"的少卖，需要更复杂的调度。
3. **Redis 集群**：Codis / Redis Cluster 分片。
4. **前端限流**：按钮置灰、验证码、答题机制，从源头减少无效流量。
5. **多层限流**：网关层 + 应用层 + 用户级（RateLimiter）多维限流。
6. **服务降级**：非核心功能（如商品详情）降级为静态页。

**面试金句**：「10 万 QPS 靠单机方案是解决不了的，必须靠**架构扩展 + 流量削减**两条路。
我更倾向于先削减流量 —— 因为**最高效的优化是不处理这个请求**。」

### Q22：如果让你重新设计，你会改什么？

**展示反思能力。**

1. **一开始就用真实 RocketMQ**，而不是内存队列。
   内存队列虽然让项目开箱即跑，但掩盖了真实 MQ 的复杂性（消息积压、死信、顺序）。
   > 不过我保留内存实现也有价值 —— 它体现了"面向接口 + 环境可移植性"的工程意识。

2. **更早接入监控告警**。我是最后才写对账逻辑，应该在做业务的同时就把
   Prometheus + Grafana 接上，用数据驱动优化而不是凭感觉。

3. **库存分片应该从一开始就设计**。现在单 key 的 Lua 扣减在极端并发下会成为热点，
   虽然后期可以改，但涉及数据迁移，成本高。

4. **单元测试覆盖率应该更高**。目前只覆盖了核心链路（~60%），
   边界情况（活动未开始、重复支付、库存恰好为 0）应该都有测试。

### Q23：你在这个项目里最难的点是什么？

**这是最能加分的题，必须讲一个真实的故事。**

**建议讲这个（我们构建过程中真实遇到的）**：

> 最难的不是写业务代码，是**保证各种异常路径下不出现数据不一致**。
>
> 我最初的设计是"先扣库存，再校验一人一单"。写完自测没问题，
> 但我在做重复下单测试时发现：**库存被扣掉了，但订单没生成** —— 少卖了。
>
> 排查后发现问题在顺序上：我先扣库存再校验用户是否已下单，
> 校验失败时直接抛异常返回，**忘了把库存加回去**。
>
> 这让我意识到一个问题：**异常路径的分支数量远超正常路径**。
> 正常路径只有一条，但异常路径有：一人一单失败、MQ 发送失败、脚本返回异常、
> 活动状态变更、Redis 超时……每一条都必须考虑"已经扣的库存怎么回滚"。
>
> 我的解决方式是引入一个原则：**"扣减"和"回滚"必须成对出现**。
> 然后我梳理了所有可能抛异常的位置，逐一确认都有对应的回滚逻辑，
> 并且给回滚脚本加了"不得超过初始库存"的保护，防止重复回滚导致库存虚高。
>
> 最后再加上定时任务对账，用"库存扣减数 == 有效订单数"这个等式做最终验证。
>
> 这件事让我理解了一句话：**分布式系统的难点不在正常流程，而在异常流程的完备性。**
