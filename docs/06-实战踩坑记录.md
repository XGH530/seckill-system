## 坑 1：Redis 版本导致幂等校验直接 500 ⭐⭐⭐⭐⭐

**这是最有价值的一个坑，强烈建议作为"我遇到最难的问题"来讲。**

### 现象

秒杀接口全部返回 500，日志里反复出现：

```
org.redisson.client.RedisException: ERR unknown command `GETDEL`,
with args beginning with: `seckill:idem:token:9e4ca188...`
```

但其他接口（登录、商品查询、库存预热）都正常。

### 排查过程

1. **先看报错信息**：`unknown command GETDEL` —— 很明确，Redis 不认这个命令
2. **怀疑是命令写错了**，去查 Redis 官方文档确认 `GETDEL` 是 6.2 版本引入的
3. **查我的 Redis 版本**：
   ```bash
   redis-cli info server | grep redis_version
   # → redis_version:5.0.14.1
   ```
4. **确认根因**：Windows 移植版 Redis（tporadowski 维护）最高只到 5.0.14，
   而 `GETDEL` 需要 6.2+，所以命令不存在

### 根因

**我使用了某个 Redis 版本才有的命令，但运行环境的版本低于该要求。**

深一层的原因：`GETDEL` 是 Redis 6.2 才加入的命令，
它把"GET + DEL"两步操作合并成一条原子命令。
我为了代码简洁直接用了 `redisTemplate.opsForValue().getAndDelete(key)`，
却没考虑部署环境的 Redis 版本。

### 解决方案

**用 Lua 脚本实现等价语义，兼容所有 Redis 版本**：

```lua
-- lua/get_and_delete.lua
local value = redis.call('GET', KEYS[1])
if value then
    redis.call('DEL', KEYS[1])
end
return value
```

```java
String value = redisTemplate.execute(getAndDeleteScript,
        Collections.singletonList(key));
```

**关键认识**：`GETDEL` 解决的核心问题是"**取值和删除必须原子**"，而不是"这个命令本身"。
只要能用 Lua 达到同样的原子性，功能上完全等价，且兼容性更好。

### 为什么"取值 + 删除"必须原子？

这是这个坑最有价值的部分。幂等 Token 的校验逻辑就是"取出并删除"：

```
非原子写法：
  时刻    请求 A                    请求 B
  T1      GET key → "1:1"
  T2                              GET key → "1:1"    ← 同一个 Token 被读了两次
  T3      DEL key
  T4                              DEL key
  结果：两个请求都认为 Token 有效 → 幂等失效 → 重复下单
```

Lua 脚本保证只有第一个请求能读到值，第二个读到 `nil`，从而正确拦截重复提交。

### 延伸思考

> 这个坑让我理解了 Redis 的一个设计思路：**它持续把"常见的复合操作"下沉为服务端原语**。
>
> 比如早期的 `SETNX` 后来演变成 `SET key value NX EX seconds`（一次搞定加锁+过期），
> `GET`+`DEL` 演变成 `GETDEL`，各类型还有 `GETEX`。
> 目的都是让客户端不必依赖 Lua 就能获得原子语义。
>
> 所以在能用到新命令时，优先用原语（更简洁、服务端优化更好）；
> 但要注意版本兼容性——特别是在生产环境，**不能假设部署的 Redis 版本和开发时一致**。
> 这是一条通用的工程原则：**不要依赖未经验证的环境假设。**

## 坑 2：Maven 中文路径导致完全无法编译 ⭐⭐⭐⭐

### 现象

```
错误: 找不到或无法加载主类 org.codehaus.plexus.classworlds.launcher.Launcher
原因: java.lang.ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher
```

Maven 装在 `D:\tools\apache-maven-3.9.9`。

### 排查过程（这个排查过程本身就有价值）

1. **先确认 Maven 本体是完好的**：
   ```bash
   ls $MAVEN_HOME/boot/
   # → plexus-classworlds-2.8.0.jar 存在，没问题
   ```

2. **手工构造命令绕过 shell 脚本**：
   ```bash
   java -classpath "C:/Users/.../plexus-classworlds-2.8.0.jar" \
     "-Dclassworlds.conf=C:/.../m2.conf" \
     "-Dmaven.home=C:/..." \
     org.codehaus.plexus.classworlds.launcher.Launcher -v
   # → 能跑起来！说明问题在 mvn 脚本本身，不在 Maven 或 Java
   ```

3. **看 mvn 脚本里的关键行**：
   ```bash
   MAVEN_PROJECTBASEDIR=`cygpath --path --windows "$MAVEN_PROJECTBASEDIR"`
   -classpath "${CLASSWORLDS_JAR}"
   ```

4. **定位根因**：`cygpath` 在中文路径下做路径转换时编码错乱，
   传出去的 `-Dmaven.home` 变成乱码路径，
   Maven 找不到 `m2.conf`，进而找不到启动类。

### 解决方案

**手工构造 java 命令，绕过有问题的 shell 脚本**：

```bat
@echo off
set "MAVEN_HOME=%USERPROFILE%\tools\apache-maven-3.9.9"
set "JAVA_HOME=%USERPROFILE%\.jdks\temurin-25"
set "CW=%MAVEN_HOME%\boot\plexus-classworlds-2.8.0.jar"
"%JAVA_HOME%\bin\java.exe" -classpath "%CW%" ^
  "-Dclassworlds.conf=%MAVEN_HOME%\bin\m2.conf" ^
  "-Dmaven.home=%MAVEN_HOME%" ^
  "-Dmaven.multiModuleProjectDirectory=%CD%" ^
  org.codehaus.plexus.classworlds.launcher.Launcher %*
```

同时把 Maven 复制到无中文路径下。

### 延伸思考

虽然是环境问题，但排查思路值得讲：

> 我的做法是**用二分法缩小范围**：
> 先确认 Maven 本体没问题（jar 都在），
> 再手工构造命令证明 Java 和 Maven 能正常启动，
> 那就只剩"mvn 这个 shell 脚本"这一层可疑。
> 去看脚本源码，果然在 `cygpath` 那行找到了问题。
>
> **关键是不瞎猜，而是用实验逐步排除可能性。**

## 坑 3：Lombok 与 JDK 25 不兼容，编译报"找不到符号" ⭐⭐⭐⭐

### 现象

编译时报几十个错误，全是同一类型：

```
找不到符号
  符号: 方法 getOrderNo()
  位置: 类型为 SeckillOrder 的变量 order
```

但代码里明明写了 `@Data`（Lombok 注解）。

### 排查过程

1. **看错误模式**：所有错误都是"找不到 getter/setter"
2. **推断**：`@Data` 没生效 → Lombok 注解处理器没运行
3. **检查 Lombok 版本**：
   ```bash
   ls ~/.m2/repository/org/projectlombok/lombok/
   # → 1.18.32
   ```
4. **确认根因**：Lombok 1.18.32 发布于 JDK 22 时代，不支持 JDK 23+。
   我用的是 JDK 25，Lombok 无法解析新的字节码版本，注解处理器静默失效。

### 解决方案

**两步都要做**：

1. **覆盖 Spring Boot 管理的 Lombok 版本**（`pom.xml`）：
   ```xml
   <properties>
       <lombok.version>1.18.40</lombok.version>
   </properties>
   ```

2. **显式声明注解处理器路径**——JDK 9+ 之后，注解处理器不再自动从 classpath 发现：
   ```xml
   <plugin>
       <groupId>org.apache.maven.plugins</groupId>
       <artifactId>maven-compiler-plugin</artifactId>
       <configuration>
           <annotationProcessorPaths>
               <path>
                   <groupId>org.projectlombok</groupId>
                   <artifactId>lombok</artifactId>
                   <version>${lombok.version}</version>
               </path>
           </annotationProcessorPaths>
       </configuration>
   </plugin>
   ```

### 延伸思考

> 这个问题让我注意到一个容易忽视的点：**JDK 大版本升级会破坏编译期的工具链**。
>
> Lombok 这类基于注解处理器的工具，需要针对每个 JDK 版本适配。
> JDK 9 引入模块系统后，注解处理器的发现机制也变了，
> 所以现在必须在 `annotationProcessorPaths` 里显式声明。
>
> 排查这类问题的通用方法是：**当"语法正确但符号找不到"时，第一反应应该是编译期工具没生效，而不是代码写错。**

## 坑 4：Tomcat 在 JDK 25 下无法启动 ⭐⭐⭐

### 现象

```
WARNING: java.lang.System::load has been called by org.apache.tomcat.jni.Library
in an unnamed module
org.springframework.context.ApplicationContextException:
Failed to start bean 'webServerStartStop'
```

### 根因

Tomcat 内嵌的 `tomcat-embed-core` 会尝试加载 JNI 本地库（APR 优化）。
JDK 25 对 `System.load` 的模块访问做了更严格的限制（JDK 24 起开始警告，
后续版本会直接禁止），导致本地库加载失败。

### 解决方案

**禁用 Tomcat 的 APR 本地库**，在启动参数中加：

```bash
java -Dtomcat.util.scan.StandardJarScanFilter.jarsToSkip=* \
     -Dorg.apache.tomcat.util.dom.TomcatDOM2Writer=... \
     -jar app.jar
```

或者更简单——**在 `application.yml` 里关掉**：

```yaml
server:
  tomcat:
    # 禁用 APR 本地库，避免 JDK 24+ 的 System.load 限制导致启动失败
    use-apr: false
```

> 💡 实际排查中我是直接加 JVM 参数绕过。
> 更规范的做法是在配置里显式关闭。

### 延伸思考

> 这暴露了一个现实问题：**JDK 的新版本会破坏老框架的底层假设**。
>
> 我的建议是：**生产项目不要盲目追新 JDK 版本**。
> 用 LTS 版本（17、21），并且先用一个最小 Demo 验证框架兼容性，
> 再决定是否升级——这叫"**升级前的兼容性验证**"，
> 比升完发现问题再回滚成本低得多。

## 坑 5：`@RequiredArgsConstructor` 与手写构造器冲突 ⭐⭐

### 现象

```
已在类 InMemoryMessageProducer 中定义了构造器
InMemoryMessageProducer(com.xgh.seckill.mq.MessageConsumer)
```

### 根因

我同时用了 Lombok 的 `@RequiredArgsConstructor`（自动生成为 `final` 字段赋值的构造器）
和手写的同名构造器（为了在构造时启动消费线程）。Lombok 生成的和我手写的签名完全一致，冲突了。

### 解决方案

**二者只能留一个**。我选择去掉 `@RequiredArgsConstructor`，保留手写构造器，
因为需要在构造时启动消费线程：

```java
public InMemoryMessageProducer(MessageConsumer messageConsumer) {
    this.messageConsumer = messageConsumer;
    // 启动消费线程
    for (int i = 0; i < 2; i++) {
        consumerPool.submit(this::consumeLoop);
    }
}
```

### 延伸思考

> Lombok 的便利性有代价：**生成的代码是隐式的，冲突时错误信息不够直观。**
>
> 我的经验是：**当一个类需要在构造时做额外初始化（比如启动线程、注册监听），
> 就不要用 `@RequiredArgsConstructor`，手写构造器更清晰。**

## 坑 6：Lua 参数被 JSON 序列化器"包引号"，导致秒杀接口 500 ⭐⭐⭐⭐⭐

**这是全项目最隐蔽的一个坑，也是最能体现排查能力的。强烈建议作为"我遇到最难的问题"来讲。**

### 现象

秒杀接口 `/seckill/do` 持续返回 500，但**其他所有接口都正常**（登录、取幂等 Token、商品查询）。

日志中的错误信息经历了两个阶段：

**阶段一**（原始写法）：
```
org.redisson.client.RedisException: ERR Error running script
@user_script:22: Lua redis() command arguments must be strings or integers
```

**阶段二**（我加了 `math.floor` 试图修复后）：
```
org.redisson.client.RedisException: ERR Error running script
@user_script:29: bad argument #1 to 'floor' (number expected, got nil)
```

**关键干扰项**：我用 `redis-cli --eval` 直接执行**同一个脚本文件**，传**同样的参数**，结果**完全正常**（正确返回 `1`）。

| 调用方式 | 结果 |
|---|---|
| `redis-cli --eval user_order_limit.lua key , "1" "86400"` | ✅ 正常返回 1 |
| `redisTemplate.execute(userOrderScript, keys, "1", "86400")` | ❌ 报错 |

**"命令行能跑、代码里报错"** —— 这是最迷惑人的现象。

### 排查过程（这是最有价值的部分）

**第 1 步：确认脚本本身没写错**

用 `redis-cli --eval` 直接跑，参数和 Java 完全一致，**返回正确结果**。
→ 结论：Lua 脚本逻辑没问题，Redis 服务端也没问题。

**第 2 步：用 SHA1 精确定位是哪个脚本**

从日志里拿到报错脚本的 SHA：`f451089852eac4ca0fcfc31b72a45aa66e8803fb`

然后用 Python 逐个计算本地脚本的 SHA1：

```python
import hashlib, os
base = 'src/main/resources/lua'
target = 'f451089852eac4ca0fcfc31b72a45aa66e8803fb'
for fn in os.listdir(base):
    raw = open(os.path.join(base, fn), 'rb').read()
    sha = hashlib.sha1(raw).hexdigest()
    print(fn, sha, '<<<< MATCH' if sha == target else '')
```

输出精确命中了 `user_order_limit.lua`，并确认了报错的第 29 行就是
`local expireSeconds = tostring(math.floor(tonumber(ARGV[2])))`。

**第 3 步：核对传入的参数**

日志里的参数列表：
```
params: [sha, 1, [seckill:order:user:...], ["1"], ["86475"]]
                  ^numkeys=1  ^KEYS        ^ARGV[1]  ^ARGV[2]
```

**两个 ARGV 都在**，那 `tonumber(ARGV[2])` 为什么会是 `nil`？

**第 4 步：想到序列化器**

既然参数"看起来正常"但 Lua 解析出 nil，那唯一可能是——
**参数在传输过程中被改变了内容**。

去看 `RedisConfig` 里 `RedisTemplate` 的配置：

```java
Jackson2JsonRedisSerializer<Object> jsonSerializer =
        new Jackson2JsonRedisSerializer<>(objectMapper, Object.class);

template.setKeySerializer(stringSerializer);       // ← key 用 String
template.setValueSerializer(jsonSerializer);       // ← value 用 Jackson JSON
```

**根因确认**：`redisTemplate.execute(script, keys, args...)` 中，
**`args` 会走 `valueSerializer`**，也就是 Jackson JSON 序列化器。

而 Jackson 序列化一个字符串 `"86475"` 时，会加上 JSON 的引号变成 `"86475"`（含字面引号）。

所以 Lua 里拿到的是：
```lua
ARGV[2] == '"86475"'   -- 引号是内容的一部分，不是语法符号！
```

于是：
- `tonumber('"86475"')` → **nil**（带引号无法转数字）
- `math.floor(nil)` → **报错**（这正是我加了 `math.floor` 之后的新错误）
- 即使不报错，`SET ... EX '"86475"'` 也是非法的

**而 `redis-cli --eval` 不经过任何序列化器，参数原样传入，所以完全正常。**

这就完美解释了"命令行能跑、代码报错"的矛盾现象。

### 解决方案

**核心思路：在 Lua 侧做参数清洗（sanitize），把外层可能存在的引号剥掉。**

这样无论调用方是否经过 JSON 序列化，脚本都能正常工作，
也让脚本与调用方的序列化配置解耦。

```lua
-- 剥离参数外层可能存在的 JSON 引号
local function sanitize(v)
    if v == nil then
        return nil
    end
    local s = tostring(v)
    -- 去掉成对的双引号（Jackson 序列化字符串时会加上）
    if string.sub(s, 1, 1) == '"' and string.sub(s, -1) == '"' then
        s = string.sub(s, 2, -2)
    end
    return s
end

local ttlRaw = sanitize(ARGV[2])
local ttl = tonumber(ttlRaw)
if ttl == nil or ttl <= 0 then
    ttl = 3600  -- 容错默认值
end
-- redis.call 只接受字符串或整数，必须转成整数字符串
local expireSeconds = tostring(math.floor(ttl))
```

**同时对项目里所有 Lua 脚本统一应用**：
`user_order_limit.lua`、`seckill_stock.lua`、`rollback_stock.lua`。

### 另一条可选路线（也值得知道）

更"正统"的做法是**让 Lua 参数不走 JSON 序列化器**：

```java
// 方案 A：改用 StringRedisTemplate 执行脚本
StringRedisTemplate stringTemplate = ...;

// 方案 B：执行脚本前显式指定参数序列化器
redisTemplate.execute(script, stringRedisSerializer, resultSerializer, keys, args);
```

**但我选择了在 Lua 侧 sanitize**，理由是：
1. 改动集中在脚本层，不侵入业务代码；
2. 脚本对调用方的配置**免疫**——以后谁改了序列化配置都不会再踩这个坑；
3. 属于"防御性编程"，比依赖"调用方记得配对序列化器"更可靠。

### 延伸思考

> 这个坑给我最大的启示是：**报错信息指向的位置，往往不是根因所在**。
>
> 错误说"Lua 第 29 行 floor 参数是 nil"，很容易让人一头扎进 Lua 里改代码。
> 但真正的根因在 Java 侧的 `RedisConfig` —— 序列化器配置。
>
> 我最后是这么定位的：
> 先证明脚本本身没问题（命令行能跑通），
> 再用 SHA1 确认报错的就是这个脚本，
> 然后核对参数发现"参数明明在，但 Lua 说 nil"，
> 这个矛盾直接指向了"**参数在传输过程中被改变了**"，
> 于是一路查到序列化器。
>
> 这让我形成一个判断原则：**当"参数存在但值为空"时，优先怀疑序列化/编码环节，而不是业务逻辑。**
>
> 另外，Redis 客户端在「普通命令参数」和「Lua 脚本参数」上走的是**不同的序列化路径**，
> 这是很多项目接入 Lua 之后才暴露的问题，值得记住。

### 顺带修正的一个设计问题：一人一单的校验顺序

排查这个 bug 的过程中，我发现原来的秒杀链路还有一个设计缺陷：

**原实现**：先扣库存 → 再校验一人一单 → 校验失败则回滚库存

```java
// 原顺序
扣库存(100 → 99);
if (已下单) {
    回滚库存(99 → 100);   // 依赖"当前库存 < 初始库存"判断，并发下可能误判
    throw 重复下单;
}
```

**问题**：
1. **一致性风险**：回滚依赖"当前库存 < 初始库存"的条件判断，
   在并发场景下可能误判，一旦回滚失败就会**少卖**（库存被扣了但没人生成订单）。
2. **无谓开销**：重复下单的用户会先扣一次再回滚一次，白白多两次 Redis 往返。

**修正后**：先校验一人一单 → 再扣库存

```java
// 修正后
if (已下单) {
    throw 重复下单;   // 此时库存尚未扣减，无需任何补偿
}
扣库存(100 → 99);
if (扣减失败) {
    撤销占位标记;      // 只撤销占位，不涉及库存，逻辑更简单
    throw 库存不足;
}
```

**改进点**：
1. 校验失败时库存根本没动，**不需要任何补偿逻辑**，天然不存在少卖；
2. 异常分支从 3 个减少到 2 个，代码路径更短；
3. **补偿面越小，系统能出错的点就越少**。

> **说明**：这类"看起来只是换了个顺序"的改动，
> 本质是在**减少分布式事务的补偿面**。
> 补偿逻辑越少 → 出错点越少 → 系统越可靠。
> 这是分布式设计的核心原则之一。

## 坑 7：压测数据全为"系统异常"——问题在压测程序而非被压系统 ⭐⭐⭐

### 现象

第一次跑并发压测，600 个请求的结果是：

```
成功请求     : 0
业务失败     : 0
系统异常     : 600   (应当为 0)
```

**全部"系统异常"**，看起来像是秒杀系统彻底崩了。

### 排查过程

**第 1 步：看 QPS 判断是否真的崩了**

```
吞吐量 QPS   : 2343.8
```

QPS 高达 2343，说明**服务响应很快，并没有崩溃**。
如果真是系统故障，QPS 会极低或有大量超时。

→ **初步判断：问题可能出在压测程序，而不是被压系统。**

**第 2 步：写一个最小探测程序，逐步验证**

写 `ProbeAscii.java`，分 4 步打印真实响应：

```java
// Step 1: 登录
// Step 2: 取幂等 Token
// Step 3: 执行秒杀
// Step 4: 查询结果
```

**第 3 步：对比探测结果与压测程序的差异**

探测程序显示：
```java
STEP1_LOGIN_STATUS=200
STEP1_JWT_LEN=-1          // ← Token 长度 -1，说明没取到！
```

**根因找到了**：我的压测程序从登录响应里取 Token 的方式错了。

登录接口返回的 `data` 是**一个对象**：
```json
{
  "code": 200,
  "data": {
    "nickname": "王五",
    "userId": 3,
    "token": "eyJhbGciOiJIUzI1NiJ9..."
  }
}
```

而我的 `extractField(body, "data")` 取的是 `data` 字段的**第一个引号对**，
结果拿到的是 `nickname` 的值（比如 `"王五"`），**而不是 JWT**。

带着 `"王五"` 这个假 Token 去请求，全部被拒 → 600 个"系统异常"。

### 解决方案

**改成直接取内层的 `token` 字段**：

```java
// 错误写法
String token = extractField(resp.body(), "data");

// 正确写法
String token = extractField(resp.body(), "token");
```

### 延伸思考

> 这件事让我养成了一个习惯：**当压测结果"太差"时，先验证压测工具本身是否正确。**
>
> 我的判断依据是 **QPS 和错误率的矛盾**：
> QPS 2343 说明服务很健康，但错误率 100%——
> 这两个指标互相矛盾，那大概率是**测量工具**的问题。
>
> 如果当时直接去"优化"秒杀系统，就会完全走错方向。

## 坑 8：`@Transactional` 加在 static 方法上，事务静默失效 ⭐⭐⭐⭐⭐

**现象**：MQ 消费者里"插入订单 + 扣减库存"明明标了 `@Transactional(rollbackFor = Exception.class)`，
但扣库存抛异常时订单**照样插进去了**，事务根本没有回滚。

**根因**：早期版本为了"让内存队列和 RocketMQ 共用一套逻辑"，把处理方法写成了
`public static void handleOrderMessage(...)`，然后直接在 **static 方法**上标 `@Transactional`。

Spring 事务的实现原理是 **AOP 动态代理**：容器启动时为目标 Bean 生成代理对象，
调用被 `@Transactional` 标注的方法时，代理先开启事务，再调用真实方法。
而 **static 方法属于类，不属于对象实例**——代理对象拦不到它，
注解就成了一行"看起来在起作用"的装饰品。**编译不报错、运行不报错、事务静默失效**，
是三种失效方式里最危险的一种。

**修复**：
1. 把处理逻辑从 static 方法改成**实例方法**（消费者实现类注入业务 Bean 后调用）；
2. 调用必须**穿过代理**——如果是 `this.method()` 自调用，事务同样不生效
   （这是同一个坑的第二张面孔，Spring 官方文档明确警告过）；
3. 用"扣库存失败 → 订单是否回滚"写了一个验证用例，确认事务真实生效。

**技术价值**：这题能区分"背过 @Transactional 概念"和"真懂事务实现"。
追问链通常是：`事务失效有哪几种场景？` → `为什么自调用会失效？` →
`代理机制是怎么工作的？` → `怎么强制走代理（AopContext.currentProxy()）？`

## 坑 9：不存在的接口返回 500「系统繁忙」而不是 404 ⭐⭐⭐⭐

**现象**：压测脚本把 `POST /seckill/do` 写成了 `POST /seckill/do/1`，
服务端返回 `{"code":500,"message":"系统繁忙，请稍后重试"}`，
监控里 `systemError` 一路上涨，看起来像服务器出了大故障。

**根因**（两层）：
1. Spring Boot 3 里，未被任何 `@RequestMapping` 匹配的路径，
   会交给 `ResourceHttpRequestHandler` **当作静态资源查找**，找不到就抛
   `NoResourceFoundException`；
2. 全局异常处理器里只有 `Exception` 兜底分支接住了它——
   URL 写错（404，客户端错误）被包装成了 500（服务端故障）。

**修复**：在 `GlobalExceptionHandler` 里为 `NoResourceFoundException`
和 `HttpRequestMethodNotSupportedException` 各加一个专门的 Handler，
返回 404 / 400 语义，**且不计入 systemError 指标**。

**为什么值得单独记一笔**：这是可观测性的经典陷阱。
"客户端用错了"和"服务端故障"混在同一个指标里，
系统错误率就失去了告警价值——真出故障时，告警早就因为噪声被忽略惯了。
**区分错误语义不是为了好看，是为了让告警可信。**

## 坑 10：DB 兜底扣库存是"死代码"——四层防线其实只有三层在工作 ⭐⭐⭐⭐⭐

**现象**：对账接口显示 `totalDeducted` 永远是 0，`t_seckill_activity.seckill_stock`
从来不随订单变化。而代码注释里明晃晃写着"第 4 层防线：数据库条件更新兜底"。

**根因**：`SeckillActivityMapper.deductStock()`（带 `WHERE seckill_stock >= 1` 的条件更新）
**定义了但全项目没有任何调用方**——消费者只插订单，从不扣 DB 库存。
更隐蔽的是，超时取消路径调用了 `rollbackStock()`（回补库存），
它的 SQL 带有 `AND seckill_stock + 1 <= initial_stock` 的守卫条件，
把"没扣过就回补"的非法操作**悄悄拦成了空操作**——守卫条件反而掩盖了缺陷。

**修复**：
1. 消费者创建订单的**同一事务**里调用 `deductStock`，第 4 层防线真正接入；
2. 行数为 0（DB 库存不足）= Redis 与 DB 漂移的极端信号 → 抛异常回滚 → MQ 重试 →
   耗尽进死信 → 人工对账；
3. 加了对账告警的闭环验证：下单后立即查询，`dbStock=99, redisStock=99, validOrderCount=1,
   consistent=true`。

**反思**：这条防线的价值不是"常驻"，而是**兜底语义必须真实存在**。
如果"DB 兜底"从未被执行过，
四层防线的叙事就整体崩塌了。
**写注释里的架构图之前，先确认代码里的每一层都真的通电。**

## 总结：这十个坑给我的方法论

| 坑 | 学到的通用原则 |
|---|---|
| Redis GETDEL | **不要依赖未经验证的环境假设**（版本、配置、依赖） |
| Maven 中文路径 | **用二分法排除可能性**，不瞎猜 |
| Lombok/JDK25 | **"语法正确但符号找不到"→ 先怀疑编译期工具** |
| Tomcat/JDK25 | **升级前先做兼容性验证**，别盲目追新版本 |
| 构造器冲突 | **框架的隐式魔法在复杂场景下会变成负担** |
| **Lua 参数被包引号** | **报错位置 ≠ 根因位置；"参数存在但值为空"→ 先怀疑序列化/编码** |
| **压测全为系统异常** | **测量结果异常时，先验证测量工具本身是否正确** |
| **static 事务失效** | **注解不是加上了就生效，要理解背后的代理机制** |
| **404 变 500** | **区分错误语义，是为了让监控告警可信** |
| **DB 兜底是死代码** | **注释里的架构 ≠ 运行中的架构，每层防线都要验证通电** |

**问题的本质**：

> 我在做这个项目时踩了 10 个坑，让我印象最深的有三个。
>
> 第一个是 Redis 版本问题。我用 `getAndDelete()` 实现幂等 Token 的原子校验，
> 本地其他接口都正常，但秒杀接口一直 500，报 `unknown command GETDEL`。
> 查下来是 Windows 版 Redis 只到 5.0.14，而 GETDEL 需要 6.2+。
> 解决方式不是换 Redis，而是用 Lua 脚本实现等价语义——
> 本质问题是"取值和删除必须原子"，能保证原子性，用什么手段不重要。
>
> 第二个更隐蔽：消费者的"插订单+扣库存"标了 @Transactional，
> 但扣库存失败时订单照样落库了。根因是我为了复用逻辑把方法写成了
> **static**——Spring 事务靠 AOP 代理实现，static 方法属于类不属于实例，
> 代理根本拦不到，事务静默失效。改成实例方法并让调用穿过代理后才修复。
> 这件事让我真正搞懂了"事务失效"背后的代理机制。
>
> 第三个最打脸：我在注释里写了"四层防超卖架构"，
> 自查时发现第 4 层——数据库条件更新兜底——**根本没有调用方**，
> 是死代码；超时回补的守卫条件还把这个问题掩盖了。
> 我把 deductStock 接进消费者事务，并写了对账验证：
> 下单后 DB 库存、Redis 库存、有效订单数三者立刻一致。
> 现在我有个习惯：**注释里的架构图，每一层都要在运行时验证"通电"**。
