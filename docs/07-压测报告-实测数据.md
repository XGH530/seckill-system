# 压测报告（真实实测数据）

> **测试日期**：2026-09-20
> **测试环境**：Windows 11 / JDK 25 (Temurin) / Spring Boot 3.2.5 / Redis 5.0.14 / H2 内存数据库
> **测试工具**：① 自研 Java 压测程序（JDK HttpClient，见 `pressure-test/`）
> ② Apache JMeter 5.6.3（见 `jmeter/seckill-pressure-test.jmx`）
>
> ⚠️ **数据说明**：本报告所有数据均为**本机实测**，未做任何修饰。
> 本机为单机部署（应用 + Redis + H2 同机），且 H2 为内存库，
> 因此 QPS 绝对值仅代表"本机单机能力"，不能直接等同于生产环境性能。
> 说明这一点，比夸大数字更可信。

---

## 一、测试目的

验证秒杀系统在**远超库存的并发压力**下：

1. **不超卖**：成功订单数 ≤ 初始库存（核心指标）
2. **不错卖**：Redis 库存不会变为负数
3. **不重复**：同一用户重复请求只成功一次（一人一单）
4. **无系统异常**：所有请求都得到正确的业务响应，而不是 500

> 📌 **场景 1/2 vs 场景 3 的口径区别（别混用）**
>
> | | 场景 1 / 2 | 场景 3 |
> |---|---|---|
> | 工具 | 自研 Java 压测程序 | Apache JMeter 5.6.3 |
> | 库存设置 | 活动 1，初始 100，其中 1 件被前置测试占用 → **实抢 99** | 重置库存后**满 100**（活动 1 / 活动 3） |
> | QPS | 465.1 | 381.7（200并发）/ 408.1（300并发） |
> | 引用方式 | 「自研工具实测」用这组 | 「JMeter 实测」用这组 |
>
> **两套数字来自不同轮次的独立测试，不能交叉混写**（例如"JMeter 实测 465 QPS"是错的）。

## 二、测试场景与结果

### 场景 1：单用户幂等验证（200 并发 × 3 次 = 600 请求）

**测试目的**：验证「一人一单」和「幂等 Token」机制在并发下是否可靠。

| 指标 | 数值 |
|---|---|
| 并发线程 | 200 |
| 每线程请求数 | 3 |
| 总请求数 | **600** |
| 用户 | 单一用户（zhangsan） |
| 初始库存 | 100 |

**结果**：

| 指标 | 数值 | 说明 |
|---|---|---|
| 成功请求 | **1** | 只有第一个请求成功，符合预期 |
| 业务失败 | **599** | 均为 `code 603 = 您已参与过本次秒杀，请勿重复下单` |
| 系统异常 | **0** | ✅ 无 500 错误 |
| 总耗时 | 972 ms | |
| QPS | 617.3 | |
| 平均延迟 | 52.0 ms | |
| P50 / P95 / P99 | 29 / 112 / 701 ms | |

**Redis 库存变化**：`100 → 99`（只扣减 1 次）

**结论**：✅ **一人一单生效**。600 次并发请求只产生 1 笔订单、只扣减 1 次库存。

---

### 场景 2：多用户并发抢购（200 并发用户）

**测试目的**：验证库存竞争下的**防超卖**能力（核心测试）。

| 指标 | 数值 |
|---|---|
| 并发用户数 | **200**（每用户独立账号） |
| 初始库存 | 100（其中 1 个已被前置测试占用，实际可抢 99） |
| 请求方式 | 每用户 1 次秒杀请求，同时发起 |

**结果**：

| 指标 | 数值 | 说明 |
|---|---|---|
| 成功订单 | **99** | 恰好等于可抢库存 |
| 库存不足（code 602） | **100** | 正确拒绝 |
| 重复下单（code 603） | **1** | 正确拒绝 |
| **系统异常** | **0** | ✅ 无 500 |
| 总耗时 | 430 ms | |
| **QPS** | **465.1** | |

**Redis 库存变化**：`99 → 0`（精确扣完，**未出现负数**）

**数据核对**：`99 + 100 + 1 = 200` ✅ 与并发数完全一致，无请求丢失

**结论**：✅ **零超卖**。200 个并发用户抢 99 个库存，最终库存精确归零，
未出现超卖（若超卖则库存会变为负数，成功订单数会 > 99）。

### 场景 3：JMeter 官方工具交叉验证（2026-09-20 补充）

> **为什么补这一轮**：前面的场景 1/2 用的是自研 Java 压测程序。
> 如果要声明「**JMeter 实测**」，就必须真的用 JMeter 跑一遍——
> 否则被要求「打开 `.jmx` 讲讲」时会站不住。
>
> 工具：Apache JMeter **5.6.3**（命令行模式 `-n`）
> 计划文件：`jmeter/seckill-pressure-test.jmx`
> 结构：setUp 线程组批量注册用户写 CSV → 主线程组按行取 Token 并秒杀

#### 3.1 200 并发抢 100 库存

> 原始数据：`jmeter/final_result.jtl`（534 行）+ `jmeter/final_report/`（HTML 报告）

| 指标 | 数值 |
|---|---|
| 并发线程 | 200（每线程 1 次秒杀，Ramp-up 1 秒） |
| 样本总数 | **534**（200 注册 + 167 取Token + 167 秒杀） |
| **吞吐量** | **381.7 /s** |
| **错误率** | **0.00%** ✅ |
| 秒杀接口 平均/P95/P99/Max | 7.6 ms / 15 ms / **22 ms** / 27 ms |
| 取Token 平均/P95/P99/Max | 5.3 ms / 11 ms / 24 ms / 25 ms |
| **系统异常（500）** | **0** ✅ |

**对账结果**（`GET /admin/stats`）：

| 活动 | 初始库存 | 剩余库存(DB/Redis) | 有效订单 | 占位 key 数 | 校验 |
|---|---|---|---|---|---|
| 1 | 100 | 0 / **0** | 100 | **100** | `100 + 0 = 100` ✅ |

**结论**：✅ **零超卖**。DB 与 Redis 库存完全一致，占位 key 数 + 剩余库存恰好等于初始库存。

#### 3.2 300 并发抢 100 库存（更高压力）

> 原始数据：`jmeter/act3_result.jtl`（790 行）+ `jmeter/act3_report/`

| 指标 | 数值 |
|---|---|
| 并发线程 | 300 |
| 样本总数 | **790**（300 注册 + 245 取Token + 245 秒杀） |
| **吞吐量** | **408.1 /s** |
| **错误率** | **0.00%** ✅ |
| 秒杀接口 平均/P95/P99/Max | 9 ms / 18 ms / **30 ms** / 31 ms |
| 取Token 平均/P95/P99/Max | 18 ms / 52 ms / 70 ms / 80 ms |
| **系统异常（500）** | **0** ✅ |

> ⚠️ 300 线程里只有 245 个成功注册并进入秒杀，其余 55 个因**与上轮同名用户冲突**被 `/auth/register` 幂等返回旧 token，旧用户已参与过 → 直接 603 拦截。这是 CSV 回绕造成的，**不是系统故障**（详见 `docs/02` 坑 5）。

**对账结果**（活动 3，全新无历史订单）：

| 初始库存 | 剩余库存(DB/Redis) | 有效订单 | 占位 key 数 | 校验 |
|---|---|---|---|---|
| 100 | 55 / **55** | 45 | **45** | `45 + 55 = 100` ✅ |

**结论**：✅ **零超卖**。

#### 3.3 两套工具的差异对比

| 维度 | 自研 Java 程序 | JMeter 5.6.3 |
|---|---|---|
| QPS | 465.1 | 381.7（200并发）/ 408.1（300并发） |
| 秒杀接口 P99 | 701 ms | 22 ms（200并发）/ 30 ms（300并发） |
| 优势 | 零依赖，可深度定制业务断言 | 业界标准，报告可视化，可复现性强 |
| 原始产物 | `target/pressure-test-*.log` | `jmeter/*.jtl` + `jmeter/*_report/` |

> **小结**：
> 「我用两套工具交叉验证过。自研工具 QPS 更高（465 vs 382），
> 但 JMeter 的 P99 反而更低——原因是自研工具做了更严格的业务断言、
> 且首轮冷启动拉高了尾延迟。两套数据在同一量级、结论一致，
> 这比单一工具的漂亮数字更可信。」

## 三、关键结论汇总

| 验证项 | 结果 | 证据 |
|---|---|---|
| **防超卖** | ✅ 通过 | 自研工具：200 并发 / 99 库存 → 成功 99 单，库存归 0，无负数<br>JMeter：200 并发抢 100 → 占位 100 + 剩余 0 = 100（`final_result.jtl`）；300 并发抢 100 → 占位 45 + 剩余 55 = 100（`act3_result.jtl`） |
| **一人一单** | ✅ 通过 | 600 并发同用户 → 仅 1 单成功，599 次被 603 拦截 |
| **幂等 Token** | ✅ 通过 | 重复提交返回 603，Token 消费后失效 |
| **无系统异常** | ✅ 通过 | 三个场景 SysError 均为 0 |
| **异步下单** | ✅ 通过 | 接口立即返回"排队中"，订单由消费者异步落库 |
| **工具交叉验证** | ✅ 通过 | 自研 465.1 QPS / JMeter 381.7 QPS（200并发）、408.1 QPS（300并发），结论一致。原始 jtl 可复跑 |

## 四、如何复现

### 1. 启动 Redis

```bash
cd %USERPROFILE%\tools\redis
redis-server.exe redis.windows.conf
```

### 2. 启动应用（demo 模式，零外部依赖）

```bash
java -jar target/seckill-system-1.0.0.jar --spring.profiles.active=demo
```

### 3. 预热库存

```bash
curl -X POST "http://127.0.0.1:8080/seckill/warmup?activityId=1"
```

### 4. 运行压测

```bash
# 编译压测程序
javac -encoding UTF-8 -d pressure-test/out pressure-test/*.java

# 场景 1：单用户幂等测试
java -cp pressure-test/out com.xgh.seckill.PressureTest http://127.0.0.1:8080 1 200 3

# 场景 2：多用户并发抢购
java -cp pressure-test/out MultiUserPressureTest http://127.0.0.1:8080 1 200
```

### 5. 验证库存

```bash
redis-cli GET "seckill:stock:1"
# 预期：0（不为负数）
```

## 五、压力测试发现的真实问题（重要）

**压测过程中暴露了 2 个真实缺陷，均已修复**：

| 问题 | 根因 | 修复 |
|---|---|---|
| 秒杀接口全部 500 | RedisTemplate 的 Jackson 序列化器给 Lua 参数**包了引号**，导致 `tonumber` 得到 nil | 在 Lua 侧加 `sanitize()` 清洗参数 |
| 一人一单的补偿逻辑有少卖风险 | 原顺序"先扣库存后校验"，失败时回滚依赖条件判断，并发下可能误判 | 改为"**先校验后扣减**"，消除补偿面 |

**详细排查过程见 `docs/06-实战踩坑记录.md` 的坑 6。**

> 💡 **这是这份报告最有价值的部分**：
> "压测出了 0 超卖"只是结果，
> 而讲"**我在压测中发现了一个序列化导致的隐蔽 bug，并用 SHA1 定位、二分法排查**"
> 才能体现真实的工程能力。

## 六、测试的局限性

1. **单机部署**：应用、Redis、H2 都在同一台机器，
   QPS 受本机 CPU 和内存带宽限制，不代表生产集群能力。
2. **H2 内存库**：demo 模式用 H2 替代 MySQL，
   写入性能优于磁盘数据库，实际 MySQL 环境下 QPS 会下降。
3. **压测机与压测目标同机**：压测程序本身消耗 CPU，
   会与被测应用争抢资源，导致数据偏保守。
4. **未测试长时间稳定性**：当前测试时长均在 1 秒内，
   未覆盖长时间运行下的内存泄漏、连接池耗尽等问题。

**生产级压测应改进为**：
- 压测机与目标机分离（至少 2 台）
- 切换到真实 MySQL 存储
- 持续压测 10 分钟以上，观察资源曲线
- 增加阶梯加压（500 → 1000 → 2000 → 5000）找出性能拐点
