### ⚠️ 关键环境说明（实测踩到的坑）

**1. `mvn` 命令不可用 → 用绝对路径绕过**

你本机的 `mvn.cmd` 依赖 `JAVA_HOME` 环境变量，该变量被工具沙箱污染了，
直接运行会报 `ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher`。

**实测可用的完整命令**（复制即用）：

```bash
java -cp "C:\Users\谁知青杉\tools\apache-maven-3.9.9\boot\plexus-classworlds-2.8.0.jar" \
  "-Dclassworlds.conf=C:\Users\谁知青杉\tools\apache-maven-3.9.9\bin\m2.conf" \
  "-Dmaven.home=C:\Users\谁知青杉\tools\apache-maven-3.9.9" \
  "-Dmaven.multiModuleProjectDirectory=C:\Users\谁知青杉\WorkBuddy\2026-09-18-09-07-45\projects\seckill-system" \
  org.codehaus.plexus.classworlds.launcher.Launcher clean package -DskipTests
```

> 💡 **更好的做法**：在 IDEA 里配置 Maven home 指向
> `C:\Users\谁知青杉\tools\apache-maven-3.9.9`，
> IDEA 不走 shell 脚本，能正常工作，比命令行舒服得多。

**2. Sentinel 的 `eager: true` 会导致 Tomcat 端口漂移**

`application.yml` 里 `spring.cloud.sentinel.eager: true` 时，
若环境无法解析主机名（打印 `Cannot determine local hostname`），
Tomcat 会**监听随机端口**而不是 8080。

**启动时显式指定端口即可规避**：

```bash
java -jar target/seckill-system-1.0.0.jar \
  --spring.profiles.active=demo \
  --server.port=8080 \
  --spring.cloud.sentinel.eager=false
```

**3. Lua 参数不能走 JSON 序列化器**（已在代码中修复）

`redisTemplate.execute()` 的 args 会经过 Jackson 序列化器被**包上引号**，
导致 Lua 里 `tonumber` 得到 nil。所有 Lua 脚本已加 `sanitize()` 修复。
**这个坑的完整排查过程见 `docs/06-实战踩坑记录.md` 坑 6，是面试的绝佳素材。**

**用 Knife4j 界面操作**（比 curl 直观）：打开 http://localhost:8080/doc.html

完整流程：

```
1. POST /auth/login           登录，拿 JWT Token（zhangsan / 123456）
```

> 💡 **重要**：从第 4 步起，所有请求都要在 Header 里带

| 实验 | 操作 | 预期结果 |

| **3. 超时回滚** | 把启动参数加 `--seckill.order-timeout-minutes=1`，下单后不支付，等 1 分钟 | 查库订单 `status=2`，Redis 库存 +1 |

**重点理解这个顺序问题**（代码里有详细注释）：

```java
// 为什么是「先校验一人一单 → 再扣库存」，而不是反过来？
// 反过来的话，重复下单时需要「回滚库存」，
// 而回滚依赖条件判断，并发下可能误判 → 少卖。
// 先校验的话，失败时库存根本没动，不需要任何补偿。
// 核心原则：补偿面越小，出错点越少。
```

## 面试中被追问的 10 个"杀手锏"问题（提前准备）

1. **"你们的库存是怎么扣的？"**
   → 别只说"用了 Redis"，要讲清三层：为什么 Redis（性能）+ 为什么 Lua（原子性）+ 为什么还要 DB 兜底（可靠性）

2. **"如果有 10 万并发，你的方案能扛住吗？"**
   → 诚实回答：单机扛不住。讲清瓶颈（Tomcat 连接数 / Redis 单线程 / DB 写入），
     以及横向扩展方案（多实例 + 网关分流 + 库存分片）

3. **"Redis 挂了怎么办？"**
   → 三层回答：① 哨兵/集群做高可用 ② DB 条件更新兜底不超卖 ③ 降级策略（限流 + 排队）

4. **"MQ 消息丢失了怎么发现？"**
   → 定时任务扫表 + 对账 SQL + 告警。**主动提"我做了对账"，加分。**

5. **"分布式锁能保证不超卖吗？"**
   → **不能！** 主从切换会丢锁。正确性靠数据库唯一索引 + 条件更新，锁只是性能优化。

6. **"为什么要异步？用户等不了怎么办？"**
   → 异步是为了削峰。用户体验用"排队中 + 轮询"解决，这是行业标准（12306、淘宝都这样）。

7. **"你这个项目有多少是抄的？"**
   → 坦然说：骨架参考了业界方案，但每个技术选型我都做了对比（比如为什么 RocketMQ 不用 Kafka），
     压测数据是我自己跑的，踩的坑都记录在 docs 里。**诚实 + 有细节 = 可信。**

8. **"如果现在让你重新设计，你会改什么？"**
   → 提前想好 2-3 点（如：一开始就用真实 MQ；应该更早接入监控；Lua 参数应该从一开始就走 String 序列化器）

9. **"你的 QPS 465 是不是太低了？"**
   → 讲清压测环境（单机、应用+Redis+H2+压测程序同机争抢 CPU），
     说明这是保守值，并给出生产级压测的改进方案。**主动说局限性，比吹数字可信。**

10. **"你在这个项目里最难的点是什么？"**
    → **这是最能加分的题。** 讲 Lua 参数被序列化器包引号那个坑：
      现象（命令行能跑、代码报 500）→ 排查（SHA1 定位 + 二分法）→
      根因（Jackson 序列化器）→ 解决（Lua 侧 sanitize）→ 收获（报错位置 ≠ 根因位置）。
