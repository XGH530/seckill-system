## 一、标准版（推荐，用于主投）

### 分布式高并发秒杀系统　独立开发　2026.09-2026.10

**技术栈**：Spring Boot 3.2.5、MyBatis-Plus 3.5.5、Redis、Lua、Redisson、RocketMQ、Sentinel、MySQL/H2、JWT、JDK 17

**项目描述**：面向高并发场景的秒杀交易系统。针对「瞬时流量与系统承载能力相差两个数量级」的核心矛盾，设计「限流过滤 → 缓存拦截 → 异步削峰 → 数据库兜底」四层防护架构，独立完成架构设计、核心链路开发、压力测试与公网部署。

**核心工作**：

- **四层防超卖体系**：设计「前端限流 → Sentinel 接口限流 → Redis Lua 原子扣减 → 数据库条件更新兜底」链路。Lua 脚本将「库存判断」与「扣减」合并为原子操作，从根本上消除"先查后改"的竞态窗口；**数据库条件更新在消费者事务内真实执行**（`UPDATE ... WHERE stock >= 1`），Redis 与 DB 任一漂移即触发回滚重试，不信任任何单点。**实测：单用户 8 并发冲击，1 单成功、7 次重复被正确拦截；下单后对账 DB 库存、Redis 库存、有效订单数三者精确一致**；JMeter 实测 200 并发抢 99 件库存，成功 99 单、库存精确归零、超卖 0 笔，平均响应 52ms、QPS 465。

- **一人一单与接口幂等**：基于「Redis Lua 原子占位 + 数据库唯一索引 `uk_user_activity` + 消费端幂等校验」三重保证。**实测 200 并发 × 3 次（共 600 请求）同一用户冲击，仅 1 单成功，599 次重复请求被正确拦截，无系统异常**。

- **异步下单削峰与最终一致性**：引入 RocketMQ 实现「扣减库存成功即返回排队中，订单由消费者异步落库」，接口响应时间从 ~50ms 降至 ~5ms，Tomcat 线程快速释放避免线程池耗尽。通过**事务消息**保证「扣库存 + 发消息」最终一致，**延迟消息**实现订单超时自动回滚库存（防少卖），配合定时任务扫表与库存对账机制兜底。同时封装抽象消息接口，支持 RocketMQ 与 Redis Stream **双实现可切换**，适配无中间件环境。

- **缓存体系设计**：实施 Cache-Aside 模式缓存热点活动数据，针对性解决**缓存穿透**（空值缓存 + 布隆过滤器）、**缓存击穿**（互斥锁重建）、**缓存雪崩**（TTL 随机抖动）三类问题。

- **分布式锁与幂等**：秒杀主链路接入自研 `@DistributedLock` 注解（AOP + Redisson），锁粒度设计为「用户+活动」——只串行化同一用户的并发请求，不同用户完全并行；实现「JVM 本地锁快速失败 + Redisson 分布式锁保正确性」双层结构，本地拦截减少无谓的 Redis 往返；含看门狗自动续期与 Lua 脚本防误删。**实测同用户 8 并发仅 1 单成交，不同用户互不受阻塞**。

- **工程化与排障**：编写自研 Java 压测程序（零额外依赖，纯 JDK HttpClient），多用户并发场景验证防超卖；自研业务指标组件（LongAdder 无锁计数 + 直方图估算 P95/P99）+ Spring Actuator 健康探针（K8s liveness/readiness）+ 运维对账接口；接口文档基于 Knife4j 自动生成。**定位并修复 10 个真实缺陷**，包括 `@Transactional` 加在 static 方法上事务静默失效、DB 兜底扣库存为死代码（四层防线实际只有三层在工作）、404 被兜底成 500 污染系统错误率等——每个缺陷都复现、修复并用接口实测验证。

**核心技术难点**：
1. **超卖根因与解决**：证明"先查库存再扣减"存在竞态窗口，采用 Redis Lua 保证原子性，并以数据库条件更新作为可靠性底线（不信任 Redis 单点）。
2. **少卖的对策**：识别出「重复下单仍扣库存」「MQ 发送失败」两条少卖路径。通过把「一人一单校验」前置到扣库存之前，使重复下单分支根本不产生补偿需求；再以延迟消息回滚 + 定时任务兜底。
3. **异步方案的代价与权衡**：分析同步下单（体验好但吞吐低）与异步下单（吞吐高但需轮询）的取舍，最终采用"排队中 + 轮询"的行业标准方案。

**演示**：本地启动 `java -jar target/seckill-system-1.0.0.jar --spring.profiles.active=demo`（账号：zhangsan / 123456）
**GitHub**：https://github.com/XGH530/seckill-system

## 三、面试口述版（自我介绍用，约 1 分钟）

> 我独立开发了一个分布式高并发秒杀系统，主要想解决高并发下的**超卖**问题。
>
> 核心方案是**四层防护**：请求先经过限流，再到 Redis 层用 Lua 脚本做原子扣减，
> 把绝大部分请求挡在数据库之前，最后数据库的条件更新做兜底。
> Lua 是关键——因为「判断库存」和「扣减库存」如果是两步操作，
> 并发下会有竞态窗口，1000 个线程可能同时通过判断，直接把库存扣成负数。
>
> 压测结果是：**200 个并发用户抢 99 件库存，最终成功 99 单，库存精确归零，超卖 0 笔**。
>
> 另外我做了**异步下单**：扣减成功后立即返回"排队中"，
> 真正的订单落库交给 RocketMQ 消费者，接口响应从 50 毫秒降到 5 毫秒左右。
>
> 做这个项目我踩了 10 个坑，印象最深的两个：
> 一个是 Lua 脚本"命令行执行正常、代码里一直 500"，
> 最后定位到 `RedisTemplate` 的 Jackson 序列化器给 Lua 参数**自动包了一层引号**，
> 我在脚本里加了参数清洗，让脚本对调用方的序列化配置免疫；
> 另一个是自查时发现注释里写的"数据库兜底扣库存"**根本没有调用方**，
> 四层防线实际只有三层在通电——我把 DB 扣减接进消费者事务，
> 并写了自动对账验证：下单后 DB 库存、Redis 库存、订单数立刻一致。
>
> 这个过程让我养成两个习惯：
> **报错位置往往不是根因位置，要顺着数据流往回查；
> 注释里的架构，每一层都要在运行时验证真的生效。**

## 四、按岗位类型调整建议

### 投递「Java 后端开发」（常规）—— 使用标准版

**面试官大概率会问**：

| 问题 | 回答要点 |
|---|---|
| Lua 为什么能保证原子性？ | Redis 单线程执行命令，Lua 脚本整个执行期间不会被其他命令打断 |
| Redis 和数据库一致性怎么保证？ | 最终一致性：Lua 扣减成功后发 MQ，消费者写库；异常路径同步回滚 + 定时任务对账补偿 |
| MQ 消息丢了/重复了怎么办？ | 不丢：生产端重试 + Broker 刷盘 + 消费端手动 ACK；不重：唯一索引 + Redis 幂等表 |
| 分布式锁为什么要校验 value？ | 防止误删他人锁：A 业务超时锁过期 → B 拿到锁 → A 执行完直接 DEL 会删掉 B 的锁 |
| 你的 QPS 465 是不是太低了？ | 见下方「诚实回答」 |
| 一人一单为什么不用分布式锁？ | 锁粒度太粗、性能差；用 SETNX 原子占位更轻量，且用唯一索引做持久层兜底 |

**关于 QPS 数字的诚实回答**（重要，能显著加分）：
> "465 这个数字是我本机单机实测的，应用、Redis、H2 内存库和压测程序都在同一台机器上，
> 会互相争抢 CPU，所以偏保守，不能代表集群能力。
> 如果做生产级压测，我会把压测机独立出来、换成真实 MySQL、
> 再做阶梯加压（500→1000→2000→5000）找出性能拐点。"
>
> **主动说明局限性，比夸大数字可信得多。**

### 投递「分布式 / 中间件方向」

**重点强化**：RocketMQ 事务消息原理、延迟消息实现、消息可靠性三要素、ShardingSphere 分片策略、雪花算法时钟回拨。

**必答**：为什么选 RocketMQ 而不是 Kafka？
> 延迟消息是 RocketMQ 内置功能，Kafka 需要自己实现时间轮；
> 秒杀场景的"订单超时回滚"是刚需，用 RocketMQ 一行配置就能搞定。

### 投递「游戏服务器 / 实时通信」方向

**秒杀项目匹配度低，建议换。** 改用 **Netty + WebSocket 多人实时对战服务端**，
秒杀项目可保留作为"高并发处理能力"的佐证。

**2026.09-2026.10 分布式高并发秒杀系统 独立开发**

**技术栈**：SpringBoot3.2.5、MyBatis-Plus3.5.5、Redis（Lua）、RocketMQ（含内存队列双实现）、Redisson、Sentinel、JWT、Knife4j、JDK17

**防超卖架构**：设计「Sentinel限流 → Redis Lua原子扣减 → 消费者事务内DB条件更新兜底」三级防护，Lua将库存判断与扣减合并为原子操作，消除"先查后改"竞态窗口；实测200并发抢99件库存，超卖0笔、库存精确归零，QPS 465、平均响应52ms。

**高并发削峰**：RocketMQ异步下单，扣减成功即返回"排队中"，接口响应由约50ms降至约5ms；延迟消息实现订单15分钟未支付自动取消并回滚DB/Redis库存，配合定时任务与库存对账接口兜底，实测三项对账（DB库存/Redis库存/有效订单数）即时一致。

**一人一单与分布式锁**：Redis Lua原子占位+数据库唯一索引双重保证，600次并发重复请求仅1单成功；秒杀主链路接入「用户+活动」粒度Redisson分布式锁（JVM本地锁快速失败+看门狗续期），同用户8并发仅1单成交、不同用户互不阻塞。

**缓存与可观测性**：Cache-Aside缓存热点活动数据，布隆过滤器+空值缓存防穿透，TTL随机抖动防雪崩；自研指标组件（LongAdder无锁计数+直方图估算P95/P99）与Actuator健康探针；独立定位并修复10个真实缺陷（含static方法事务静默失效、DB兜底死代码）。
